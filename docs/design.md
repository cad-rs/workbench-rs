\# workbench-rs：通用工程桌面应用框架需求与设计



\- \*\*项目名称：\*\* `workbench-rs`

\- \*\*文档状态：\*\* 初版设计基线

\- \*\*目标语言：\*\* Rust

\- \*\*目标应用类型：\*\* CAD、机械设计、工业仿真、多物理场仿真及其他专业工程桌面应用

\- \*\*GUI 候选：\*\* egui、GPUI

\- \*\*产品 GUI 规则：\*\* 每个已发布产品在开发和构建时固定选择一种 GUI；最终用户不能选择或切换 GUI

\- \*\*可选渲染能力：\*\* `wgpu`

\- \*\*用户插件语言：\*\* Python



\---



\## 1. 文档目的



本文定义 `workbench-rs` 的需求和架构设计。



`workbench-rs` 是一套可复用的通用 Workbench 框架，用于开发多个\*\*彼此独立的专业桌面应用\*\*。它提供通用桌面应用基础设施、Workbench 组合机制和插件扩展接口，但不内置 CAD、装配、网格、材料或求解器等领域能力。



产品团队可以从多个领域 Workbench 中选择所需模块，组合成独立应用；最终用户则可以通过 Python 插件扩展产品开放的功能点。



\---



\## 2. 核心目标



\### 2.1 产品目标



`workbench-rs` 应支持开发多个独立产品，例如：



\- 类似 FreeCAD 的可扩展 CAD 应用；

\- 类似 SolidWorks 的机械设计应用；

\- 类似 COMSOL 的仿真与后处理应用。



这些是产品方向示例，不表示框架本身提供了达到对应产品水平的 CAD 内核、仿真能力或文件格式兼容性。



\### 2.2 框架目标



框架应提供：



1\. 可组合的 Rust Workbench 模块机制；

2\. 典型工程桌面界面：RibbonBar、四周可停靠面板和中央多标签内容区；

3\. 命令、菜单、RibbonBar、快捷键、面板、视图和文档类型等扩展点；

4\. 与具体 GUI 框架解耦的平台 API；

5\. 多种视图呈现方式；`wgpu` 是可选渲染能力，不是所有视图的强制要求；

6\. Rust 视图扩展按需获取受控的 `wgpu` 渲染上下文；

7\. 支持同步、异步及后台执行的命令系统；

8\. 统一的任务生命周期、进度、取消和错误反馈；

9\. Python 插件的发现、加载、生命周期管理和扩展能力；

10\. 文档、任务、设置、日志和事件等通用应用服务；

11\. 产品构建时选择 GUI 前端并组合 Workbench 模块；

12\. 多个独立产品共享平台代码，同时保留各自的产品配置和发行物。



\### 2.3 设计原则



\- \*\*平台不包含领域语义。\*\* 平台不定义 CAD 特征、物理场、材料模型或求解器模型。

\- \*\*产品显式组合模块。\*\* 产品决定包含哪些 Workbench、插件能力和默认布局。

\- \*\*领域模块通过稳定接口协作。\*\* 避免跨领域模块访问彼此的内部实现。

\- \*\*GUI 可替换，产品 GUI 固定。\*\* 每个产品构建并交付一种 GUI 前端。

\- \*\*渲染方式按视图选择。\*\* 普通面板和内容视图不必使用 `wgpu`。

\- \*\*命令入口与执行方式分离。\*\* RibbonBar、菜单、快捷键和 Python 插件均通过同一命令系统执行操作。

\- \*\*长任务不阻塞界面。\*\* 后台任务通过消息或受控命令提交结果。

\- \*\*先静态组合，后动态扩展。\*\* Rust Workbench 初期采用 Cargo 编译组合；Python 插件提供运行时扩展。

\- \*\*明确插件能力边界。\*\* 进程内 Python 插件不被视为安全沙箱。

\## 3. 范围与非目标



\### 3.1 框架范围



`workbench-rs` 负责：



\- 应用生命周期、产品配置和 Workbench 模块组合；

\- GUI 前端适配；

\- RibbonBar、菜单、快捷键和命令面板；

\- Dock Panel、中央多标签内容区和布局管理；

\- 视图注册、生命周期和呈现方式扩展；

\- 可选的 `wgpu` 渲染基础设施；

\- 文档与项目的通用设施；

\- 命令执行、撤销/重做和事务边界；

\- 后台任务、进度、取消和日志；

\- 插件清单、发现、加载、错误处理和 API 版本管理；

\- 设置、诊断、事件和测试设施。



\### 3.2 非目标



通用框架不负责：



\- CAD 几何内核、B-rep、草图约束、特征树或拓扑命名；

\- 装配求解、工程图、制造或特定行业工作流；

\- 有限元、计算流体力学、多物理场等求解器；

\- 网格生成、材料数据库或物理场模型；

\- 与任何商业产品完全兼容的文件格式；

\- Python 插件的默认安全沙箱；

\- 早期阶段的 Rust 动态库插件 ABI；

\- 保证 egui 与 GPUI 的控件实现、视觉效果或内部状态完全一致；

\- 强制所有视图或面板使用 `wgpu`；

\- 允许 Python 插件直接操作原始 `wgpu` 资源。

\## 4. 名词定义



\### 4.1 Platform（平台）



`workbench-rs` 提供的通用应用运行时及其 API，负责命令、上下文、文档基础设施、插件生命周期、后台任务、持久化基础服务、工作区和 GUI 前端接口。



\### 4.2 Workbench 模块



一个可编译进产品的 Rust 功能模块。它可以注册命令、RibbonBar 项目、面板、视图、文档类型、导入导出器和服务。



Workbench 模块不必等同于一个屏幕布局。



\### 4.3 RibbonBar



位于应用主窗口中的功能区控件。由 Tab、Group 和具体 Action/Control 构成。Workbench 可以贡献功能区内容；平台负责统一布局、命令绑定和状态管理。



\### 4.4 Dock Panel



停靠在主窗口四周的可组合面板。可以移动、调整尺寸、折叠、隐藏、浮动或重新停靠。



\### 4.5 中央内容标签



中央多标签内容区中的一个标签实例，可承载文档编辑器、工程视图、图表、表格、文本或其他主要工作内容。



\### 4.6 Perspective / 工作模式



一组工作流和界面组织配置，例如启用哪些面板、默认布局、RibbonBar 显示策略和视图布局。



\### 4.7 Product（产品）



使用 `workbench-rs` 构建的独立桌面应用。产品选择 GUI 前端、Workbench 模块、默认工作模式、产品外观和发行配置。



\### 4.8 Python 插件



在应用运行时由宿主发现和加载的用户扩展。插件通过稳定的 Python Host API 贡献功能，不依赖 Rust 内部类型、GUI 框架控件或原始 GPU 资源。

\## 5. 总体架构



```text

┌────────────────────── 独立产品层 ──────────────────────┐

│ 产品 A：构建时选择 egui，组合 CAD Workbench              │

│ 产品 B：构建时选择 GPUI，组合 Assembly / Drawing         │

│ 产品 C：构建时选择一种 GUI，组合 Simulation / Results    │

│ 产品配置：模块、Ribbon、布局、插件策略、发行配置          │

├────────────────────── Workbench 模块层 ────────────────┤

│ Sketch │ Part │ Assembly │ Drawing │ Simulation │ Results│

│ 贡献领域命令、Ribbon、面板、视图、文档类型和服务          │

├────────────────────── 通用平台层 ───────────────────────┤

│ 模块注册 │ 命令与事务 │ 文档 │ 上下文 │ 任务与进度       │

│ 插件 Host API │ 事件 │ Ribbon 模型 │ 工作区 │ 设置/日志   │

├────────────────────── GUI 与渲染层 ─────────────────────┤

│ egui 或 GPUI 前端（产品构建时选择一种）                    │

│ 窗口、输入、Ribbon、Dock、内容标签的具体适配               │

│ 可选的 wgpu 渲染服务与视图调度                             │

├────────────────────── 系统基础层 ───────────────────────┤

│ 窗口与输入 │ GPU │ 文件系统 │ OS 集成 │ 崩溃诊断           │

└─────────────────────────────────────────────────────────┘



Rust Workbench 视图 ──按需使用渲染 API──> 宿主渲染服务

Python 插件 ──稳定 Host API──> 通用平台

通用平台 ──UI 模型──> 产品选定的 GUI 前端

```



\### 5.1 依赖方向



```text

产品组合

&#x20; ├── 依赖通用平台

&#x20; ├── 依赖所选 GUI 适配器

&#x20; └── 依赖所选 Workbench 模块



Workbench 模块

&#x20; └── 依赖平台 API 和其明确声明依赖的领域 API



GUI 适配器

&#x20; └── 依赖平台 UI 模型和 GUI 框架



渲染服务

&#x20; └── 在产品启用相关能力时提供 GPU 渲染资源和调度



Python 插件

&#x20; └── 依赖版本化的 Python Host API

```



平台核心不得依赖任何 CAD、CAE 或其他领域模块。领域模块不得直接依赖另一领域模块的内部 crate。

\## 6. 主窗口与工作区布局



\### 6.1 主窗口结构



主窗口采用典型的工程桌面应用布局：



```text

┌──────────────────────────────────────────────────────────┐

│ RibbonBar                                                │

├────────────┬───────────────────────────────┬─────────────┤

│            │                               │             │

│ 左侧 Dock  │       中央多标签内容区         │ 右侧 Dock   │

│ Panel      │  \[文档 A] \[视图 B] \[文档 C]     │ Panel       │

│            │                               │             │

├────────────┤                               ├─────────────┤

│            │                               │             │

│ 左下 Dock  │                               │ 右下 Dock   │

│ Panel      │                               │ Panel       │

├────────────┴───────────────────────────────┴─────────────┤

│ 状态栏 / 任务状态 / 进度提示                              │

└──────────────────────────────────────────────────────────┘

```



主窗口包括：



1\. \*\*顶部 RibbonBar\*\*：提供当前产品和工作模式下的主要命令入口。

2\. \*\*四周 Dock 区域\*\*：主窗口左、右、上、下方向的停靠区域。

3\. \*\*中央多标签内容区\*\*：显示打开的文档、编辑器和视图。

4\. \*\*状态与任务区域\*\*：显示当前上下文、后台任务状态、进度、取消操作和必要通知。



Dock Panel 的具体内容和默认位置由产品配置及 Workbench 模块决定。平台不要求所有产品使用相同的初始布局。



\### 6.2 Dock Panel



工作区管理器应支持：



\- 停靠在左、右、上、下区域；

\- 在同一区域将多个面板组合为标签；

\- 调整尺寸、折叠、隐藏和重新显示；

\- 浮动为独立面板并重新停靠；

\- 保存和恢复用户布局；

\- 由 Workbench 或插件注册面板；

\- 设置默认停靠区域、默认尺寸和适用工作模式；

\- 所属模块或插件不可用时，忽略失效布局项并提供诊断。



面板使用稳定的 `PanelId` 注册，注册信息可包含标题、图标、默认停靠建议、适用上下文和创建入口。平台负责面板生命周期与布局管理，所选 GUI 前端负责具体呈现。



\### 6.3 中央多标签内容区



中央内容标签可以承载：



\- 文档编辑器；

\- CAD 或仿真领域视图；

\- 图表、表格、文本和报告；

\- 产品定义的其他主要内容。



平台应管理内容实例的打开、激活、关闭、重排和恢复，并在切换活动标签时更新当前应用上下文。



中央内容区应支持：



\- 多个文档或视图同时打开；

\- 标签切换和激活上下文更新；

\- 标签重排；

\- 关闭及未保存状态提示；

\- 标签上下文菜单；

\- 产品定义的会话恢复策略。



第一阶段要求支持中央多标签。中央区域拆分为多个并列标签组可作为后续能力，不是初始架构的强制要求。



\### 6.4 RibbonBar 与工作区上下文



\- 活动文档、活动视图、选择集和工作模式构成当前命令上下文；

\- 命令系统根据上下文提供命令的启用、禁用、勾选和可见状态；

\- Workbench 可以贡献 RibbonBar Tab、Group 和命令项；

\- 产品可以定义默认 Tab 顺序、默认工作模式和布局；

\- Dock Panel 或中央标签切换后，平台更新当前上下文；

\- RibbonBar 不直接修改领域文档状态，操作统一通过命令系统执行。



\### 6.5 布局持久化



工作区布局持久化应使用稳定的面板 ID、视图类型 ID 和内容标识，而不是 GUI 框架内部控件 ID。



至少保存：



\- Dock Panel 的停靠区域、顺序、大小、显示状态和浮动状态；

\- 中央标签的顺序、活动标签和可恢复内容标识；

\- 当前工作模式；

\- RibbonBar 活动 Tab 或产品允许保存的显示偏好。



插件或 Workbench 缺失时，平台应跳过无法恢复的布局项，并允许用户重置布局。



\### 6.6 GUI 前端关系



平台定义 UI 无关的 RibbonBar、Dock Panel、中央标签和布局模型。egui 或 GPUI 前端分别负责实现其交互与绘制。



\- 领域 Workbench 不依赖 GUI 框架内部控件；

\- 单个产品构建并发布时固定选择一种 GUI；

\- 两种 GUI 的布局实现细节不要求完全一致；

\- 两种 GUI 应通过共同的布局行为验收测试。



\### 6.7 视图呈现方式



中央内容标签所承载的视图可以采用不同呈现方式。普通表单、属性面板、图表、文本或表格不要求使用 `wgpu`。需要 GPU 加速的视图可以按需选择 GPU 渲染能力。

\## 7. RibbonBar 功能区设计



\### 7.1 设计目标



RibbonBar 是主窗口的一等界面扩展点。平台管理通用结构和命令绑定，Workbench 模块和 Python 插件通过稳定 API 贡献内容。



\### 7.2 结构模型



```text

RibbonBar

&#x20; ├── Tab

&#x20; │    ├── Group

&#x20; │    │    ├── Command Button

&#x20; │    │    ├── Toggle / Check Button

&#x20; │    │    ├── Split Button

&#x20; │    │    ├── Menu Button

&#x20; │    │    └── 受限的声明式 Control

&#x20; │    └── ...

&#x20; └── Contextual Tab（可选）

```



平台模型应支持：



\- Tab 和 Group 的稳定 ID；

\- 标题、图标、排序和分组；

\- 命令按钮与命令 ID 绑定；

\- 命令启用、禁用、勾选和可见状态；

\- Split Button 和下拉菜单；

\- 工作模式、文档类型或选择上下文相关的 Tab；

\- Workbench 和插件对现有 Tab/Group 的受控贡献；

\- 空间不足时的紧凑呈现或溢出；

\- 快捷键和键盘导航约定；

\- 产品默认配置和用户显示偏好。



\### 7.3 扩展规则



\- Ribbon 项目使用稳定 ID，并通过命令 ID 绑定命令；

\- Python 插件通过平台 API 贡献 Tab、Group 或命令入口；

\- 插件不得直接修改其他模块注册的控件实现；

\- 向已有 Tab/Group 扩展时必须声明目标 ID；

\- 目标不存在时应产生可诊断的注册结果；

\- 命令状态和执行结果由命令系统统一提供；

\- 产品可以禁用、排序或设置扩展项目的默认显示状态。



\### 7.4 示例



```rust

RibbonTab {

&#x20;   id: "part.model",

&#x20;   title: "Model",

&#x20;   groups: vec!\[

&#x20;       RibbonGroup {

&#x20;           id: "part.create",

&#x20;           title: "Create",

&#x20;           items: vec!\[

&#x20;               RibbonItem::Command {

&#x20;                   command: "part.create\_box",

&#x20;               },

&#x20;               RibbonItem::Command {

&#x20;                   command: "part.create\_cylinder",

&#x20;               },

&#x20;           ],

&#x20;       },

&#x20;   ],

}

```



该示例只表达数据模型意图，不代表最终 Rust API 签名。

\## 8. Workbench 模块设计



\### 8.1 Rust Workbench 模块职责



Workbench 模块可以贡献：



\- 命令、参数、适用上下文和执行逻辑；

\- RibbonBar Tab、Group、命令入口和快捷键；

\- 菜单和上下文操作；

\- Dock Panel 与中央内容视图；

\- 文档类型及领域数据服务；

\- 导入器、导出器和文件过滤器；

\- 工作模式与布局建议；

\- 后台任务类型；

\- 诊断信息和产品内帮助入口。



Workbench 模块不得：



\- 直接修改其他模块的内部状态；

\- 假设自身必然包含在所有产品中；

\- 绕过平台 API 私自创建全局 UI；

\- 将领域对象强行纳入平台通用数据模型。



\### 8.2 Rust 模块组合



第一阶段 Rust Workbench 通过 Cargo workspace crate 组织，并在产品构建时链接进应用。产品代码显式装配启用模块。

\## 9. 视图与渲染设计



\### 9.1 设计目标



平台定义通用的视图注册、生命周期、布局和上下文机制，但不要求所有视图采用相同的渲染技术。



视图可以选择：



\- 当前 GUI 前端的原生控件；

\- GUI 前端提供的绘制接口；

\- CPU 绘制的画布或图像；

\- `wgpu` GPU 绘制；

\- 后续接入的其他专用渲染后端。



平台的“视图”与具体“渲染器”应分开建模。



\### 9.2 通用视图扩展点



视图扩展可以：



\- 注册稳定的视图类型 ID；

\- 声明名称、图标、适用文档类型和创建入口；

\- 创建、更新和销毁视图实例；

\- 接收尺寸、缩放、焦点、输入和上下文变化；

\- 声明所需的呈现方式或渲染能力；

\- 使用对应呈现方式的宿主 API；

\- 报告初始化、更新和绘制错误。



普通视图不必实现 GPU 初始化、设备访问或渲染生命周期回调。



\### 9.3 渲染能力



渲染能力由视图按需声明，由平台或产品提供。能力可以包括：



\- GUI 原生控件；

\- GUI 前端绘制接口；

\- CPU 图像或画布绘制；

\- `wgpu` GPU 绘制；

\- 后续扩展的其他渲染后端。



产品可以根据目标平台、性能要求和已启用能力决定某项视图是否可用。能力不可用时，平台应提供诊断，或允许视图选择受支持的降级实现。



\### 9.4 `wgpu` 视图扩展



需要 GPU 渲染的 Rust 视图可以声明 `wgpu` 能力，并在宿主提供的渲染生命周期中访问受控上下文。上下文可以包含：



\- `wgpu::Device` 和 `wgpu::Queue`；

\- 当前视图的渲染目标或平台定义的绘制接口；

\- 视口尺寸、缩放和表面格式等元数据；

\- 资源创建、缓存和设备重建相关服务；

\- 渲染诊断接口。



`wgpu` 上下文只传给明确声明并实现对应 GPU 扩展接口的 Rust 视图，不属于通用视图 API 的必需部分。



平台负责协调 GPU 资源生命周期、视图关闭、窗口尺寸变化、表面重建及设备丢失。扩展不得假定设备或临时帧资源永久有效。



\### 9.5 Python 视图扩展



Python 插件不直接获取 `wgpu::Device`、`wgpu::Queue`、Surface、纹理视图或命令编码器。



Python 插件可以通过较高层级接口扩展视图，例如：



\- 注册声明式面板、表格或图表；

\- 提交场景数据，由宿主或领域 Workbench 绘制；

\- 添加标注、颜色映射或可视化配置；

\- 使用宿主提供的受限绘制指令或叠加层 API；

\- 将耗时数据处理作为后台任务执行，再将结果交给宿主显示。

\## 10. 命令、异步执行与后台任务



\### 10.1 命令系统目标



命令是 RibbonBar、菜单、快捷键、Python 插件和自动化操作的统一执行入口。调用方不应关心命令运行在线程、异步执行器还是后台进程中。



平台应支持：



\- 稳定命令 ID；

\- 参数定义和校验；

\- 当前上下文与启用条件；

\- 立即完成的轻量命令；

\- 异步命令；

\- 提交为后台任务的长耗时命令；

\- 命令执行状态、进度、取消和错误传播；

\- 通过命令统一执行文档变更；

\- 可逆命令的撤销/重做；

\- 命令与 RibbonBar、菜单、快捷键和 Python API 解耦。



\### 10.2 执行状态



```text

Pending

&#x20; ├── Running

&#x20; │    ├── Succeeded

&#x20; │    ├── Failed

&#x20; │    └── Cancelled

&#x20; ├── Failed

&#x20; └── Cancelled

```



命令可以立即结束，也可以返回异步执行句柄或后台任务句柄。平台负责跟踪其生命周期。



\### 10.3 进度反馈



命令或任务可以报告：



\- 任务标题和可选描述；

\- 当前阶段或子任务名称；

\- 可选的确定进度值；

\- 不确定进度状态；

\- 成功、失败或取消结果；

\- 诊断日志和错误详情；

\- 是否允许用户取消。



界面可根据任务状态提供：



\- 状态栏或任务区域中的进度；

\- 任务面板中的阶段、进度和日志；

\- 取消按钮；

\- 完成、失败或取消通知；

\- RibbonBar 命令或相关 UI 元素的运行状态。



命令不得直接依赖 egui 或 GPUI 的进度控件。具体展示由所选 GUI 前端完成。



\### 10.4 取消与错误处理



\- 可取消命令应检查取消信号或任务上下文；

\- 取消是协作式的，不承诺可强行中断任意计算；

\- 取消后应有明确终态，并尽可能清理临时资源；

\- 错误应包含可读说明和可诊断详情；

\- 插件异常应被宿主捕获并显示，不能无提示地终止主应用；

\- 任务状态应供日志、自动化测试和产品诊断查询。



\### 10.5 后台任务与文档事务



后台命令不得在任意线程直接修改 UI 或共享文档内部状态。推荐流程：



1\. 命令在受控上下文中读取输入并创建任务；

2\. 后台任务执行计算，不持有不受控的可变 UI/文档引用；

3\. 任务通过消息返回结果或候选变更；

4\. 宿主在适当的文档事务边界提交变更；

5\. 可撤销操作记录撤销所需信息；

6\. 文档已关闭、已更新或任务已取消时，宿主按明确策略拒绝或重新校验提交。



平台应提供必要的文档版本或变更序号机制，防止后台任务基于过期输入覆盖用户的新操作。具体冲突处理策略由领域模块参与定义。



\### 10.6 命令调用路径



```text

RibbonBar / 菜单 / 快捷键 / Python API

&#x20;                 │

&#x20;                 ▼

&#x20;             命令注册表

&#x20;                 │

&#x20;                 ▼

&#x20;      上下文检查、参数校验、执行

&#x20;                 │

&#x20;       ┌─────────┴─────────┐

&#x20;       ▼                   ▼

&#x20;  立即完成             异步 / 后台任务

&#x20;                           │

&#x20;               进度、取消、日志、结果

&#x20;                           │

&#x20;                           ▼

&#x20;                    文档事务提交

```

\## 11. Python 插件机制



\### 11.1 目标



用户可以使用 Python 插件扩展产品开放的命令、RibbonBar、菜单、快捷键、面板、视图、导入导出和事件处理能力。



插件面向稳定 Host API，而不是 Rust crate 私有实现、GUI 控件或原始 GPU 资源。



\### 11.2 插件清单示例



```toml

\[plugin]

id = "com.example.mesh-tools"

name = "Mesh Tools"

version = "0.1.0"

api\_version = "1"

entry\_point = "plugin.py:register"



\[compatibility]

products = \["product-cad"]

platform = ">=0.1.0"



\[permissions]

document\_read = true

document\_write = true

filesystem\_read = false

network = false

```



清单字段可随实现演进。插件 ID 必须稳定且唯一。权限声明用于能力管理、用户提示和审计，不构成进程内 Python 的安全沙箱。



\### 11.3 插件扩展点



第一阶段建议支持：



\- 命令注册；

\- RibbonBar Tab、Group 和命令项贡献；

\- 菜单、工具栏和快捷键贡献；

\- 启用条件和上下文过滤；

\- 参数 schema 与命令输入；

\- 声明式面板；

\- 受限的视图贡献和可视化叠加层；

\- 文档读访问与通过宿主命令修改文档；

\- 异步命令和后台任务；

\- 进度报告与取消协作；

\- 有版本的事件订阅；

\- 导入器和导出器注册；

\- 插件设置、日志和错误报告。



\### 11.4 Python API 示例



```python

def register(api):

&#x20;   api.commands.register(

&#x20;       id="mesh.refine",

&#x20;       title="Refine Mesh",

&#x20;       callback=refine\_mesh,

&#x20;   )



&#x20;   api.ribbon.add\_command(

&#x20;       tab="mesh",

&#x20;       group="mesh.modify",

&#x20;       command="mesh.refine",

&#x20;   )





async def refine\_mesh(context, parameters):

&#x20;   task = context.tasks.current()

&#x20;   task.set\_title("Refine mesh")



&#x20;   for step in range(10):

&#x20;       task.check\_cancelled()

&#x20;       await refine\_one\_step(context, parameters, step)

&#x20;       task.report\_progress((step + 1) / 10)



&#x20;   return context.document.apply\_command(

&#x20;       "mesh.refine\_document",

&#x20;       parameters,

&#x20;   )

```



示例用于说明接口意图，不代表最终 API 签名。正式 API 应明确约定异步回调、解释器限制、错误、取消、进度和文档提交行为。



\### 11.5 插件运行与安全边界



\- 宿主负责插件发现、加载、初始化、禁用和卸载；

\- Python 回调通过受控 Host API 调用平台能力；

\- 文档变更通过命令或事务提交；

\- 长耗时操作使用任务 API；

\- 插件异常被捕获并写入日志和诊断信息；

\- API 版本不兼容时拒绝加载并说明原因；

\- 进程内 Python 插件不视为安全沙箱；

\- 若需要运行不可信插件，应另行设计独立进程及 IPC 隔离模型。



\### 11.6 插件 UI 与渲染约束



\- 插件不得依赖具体 GUI 框架对象；

\- 常规插件面板优先使用声明式 UI；

\- Python 视图插件通过场景数据、标注、叠加层或高层可视化 API 扩展；

\- Python 插件不直接持有 `wgpu` 原生资源；

\- 任意 Python 原生绘制和复杂自定义控件不属于第一阶段承诺。

\## 12. 通用平台服务需求



\### 12.1 文档与项目基础设施



平台提供：



\- 新建、打开、保存、另存、关闭和恢复；

\- 文档对象的稳定 ID；

\- 未保存状态跟踪；

\- 文件格式版本与迁移入口；

\- 多文档上下文；

\- 文档级插件数据的隔离和命名；

\- 自动保存和崩溃恢复扩展点。



领域文档 schema 由领域模块定义。平台不得把内部 Rust 对象布局直接作为长期文件格式。



\### 12.2 事务与撤销/重做



\- 命令通过定义清楚的事务边界提交变更；

\- 可撤销命令明确保存或推导撤销所需数据；

\- 大型领域数据不强制使用昂贵的全量复制；

\- 事务失败应避免留下半完成状态；

\- 撤销历史与文档生命周期关联；

\- 支持明确声明不可撤销的操作。



\### 12.3 上下文、事件和选择



\- 当前产品、文档、窗口、中央内容、工作模式由平台上下文表达；

\- 领域选择模型由领域模块扩展；

\- 事件具有稳定 ID、版本和明确生命周期；

\- 插件卸载时清理其事件订阅；

\- 不将高频渲染事件作为通用插件事件广播。



\### 12.4 设置、日志和诊断



平台提供：



\- 应用级、产品级、用户级和插件级设置命名空间；

\- 结构化日志及级别过滤；

\- 插件加载、命令、任务和视图错误诊断；

\- 任务与文档关联日志；

\- 运行时配置诊断；

\- 自动化测试可查询的任务和错误状态接口。

\## 13. 产品组合与构建



\### 13.1 产品责任



每个产品定义：



\- 唯一产品 ID、名称、图标和发行配置；

\- 选用的一个 GUI 前端；

\- 启用的 Workbench 模块；

\- RibbonBar 默认 Tab、Group 和布局；

\- 默认工作模式、Dock Panel 和中央标签策略；

\- 产品提供的文档类型与文件关联；

\- 可安装插件的范围与策略；

\- Python 运行时及插件分发策略。



\### 13.2 构建选择



GUI 选择在产品配置或构建阶段确定。可以使用独立产品 crate、Cargo feature 或产品构建配置表达选择，但最终产品二进制应只有一个实际 GUI 前端实现。

```toml
&#x20;   "sketch",

&#x20;   "part",

&#x20;   "drawing",

]

python = true

allowed\_sources = \["user", "bundled"]

```



此配置表达产品装配意图；最终实现也可以采用 Rust 产品 crate 的静态类型装配。

\## 15. API 与兼容性要求



\- 公共平台 API 应尽量小、语义明确，并区分稳定、实验性和内部接口。

\- 插件 API 使用明确版本；插件清单声明兼容范围。

\- Rust 内部类型不得自动成为插件稳定接口。

\- 序列化 schema 显式带版本，并支持迁移。

\- 命令、事件、文档类型、Ribbon 项目、面板和视图使用稳定 ID。

\- 移除或变更插件 API 时提供兼容策略和可读诊断。

\- GUI 适配器和渲染服务通过自动化测试验证平台契约。

\- 不以 Rust 动态库 ABI 作为第一阶段插件承诺。

\- `wgpu` 原生接口属于受控的 Rust 扩展能力，不直接暴露给 Python 插件。

\- 任务和进度 API 不依赖 GUI 前端控件类型。

\- 未声明 GPU 能力的视图无需实现或依赖 `wgpu` 接口。



\---



\## 16. 非功能性需求



\### 16.1 可维护性



\- 核心 crate 避免循环依赖；

\- 领域 crate 不依赖 GUI 实现细节；

\- 插件 API 有文档、示例和版本说明；

\- 产品配置可审计启用模块、渲染能力和 GUI 前端。



\### 16.2 稳定性



\- 插件失败不得无提示地导致主应用崩溃；

\- 后台任务错误、取消和完成状态必须可见；

\- 文档保存失败必须保留未保存状态；

\- 插件卸载时清理命令、Ribbon 项目、事件订阅和面板注册；

\- GPU 视图在设备或表面重建时遵守约定的资源恢复流程；

\- 普通非 GPU 视图不受 GPU 设备不可用影响。



\### 16.3 性能



\- 长耗时工作不得阻塞 UI 响应；

\- 平台事件避免不必要的高频全局广播；

\- 文档基础设施不强制每次编辑复制整个领域模型；

\- 渲染服务只为选择 GPU 渲染能力的视图提供相关资源；

\- 任务服务为大规模计算和领域并行执行留出接入点。



\### 16.4 可测试性



\- 平台核心尽量可在不启动真实窗口的情况下测试；

\- 命令注册、异步状态、进度、取消、插件清单和 API 兼容均有测试；

\- GUI 前端、工作区布局和 GPU 视图生命周期有相应测试；

\- 至少一个示例 Python 插件进入持续集成测试；

\- 产品装配配置有依赖和扩展点校验。

\## 17. 验收标准



第一阶段框架原型达到以下条件时，可认为核心架构得到初步验证：



1\. 可编译一个独立产品，并在构建时明确选定一种 GUI。

2\. 产品可以装配一个 Rust Workbench 模块。

3\. 主窗口包含 RibbonBar、四周 Dock 区域、中央多标签内容区和状态/任务反馈区域。

4\. Workbench 可以注册 RibbonBar Tab、Group、命令项、Dock Panel、中央内容视图和工作模式。

5\. RibbonBar 命令与平台命令系统共用启用状态和执行入口。

6\. 平台可以在中央多标签区打开、激活、重排和关闭不同类型的内容。

7\. 切换中央活动标签后，平台更新命令上下文及 RibbonBar 命令状态。

8\. Dock Panel 和中央标签布局使用稳定 ID 保存与恢复。

9\. 缺失插件或 Workbench 的布局项不会导致应用启动失败。

10\. 视图可以使用适合其内容的呈现方式，不要求所有视图使用 `wgpu`。

11\. 只有明确需要 GPU 渲染的 Rust 视图扩展才能访问受控的 `wgpu` 渲染上下文。

12\. Python 插件可以通过清单被发现，并注册命令和 Ribbon 项目。

13\. Python 插件不能直接取得 `wgpu` 原生 GPU 资源。

14\. 命令可立即完成，也可异步或提交为后台任务。

15\. 任务能够报告进度、接受协作式取消请求并返回明确终态。

16\. UI 能够呈现任务进度、错误和取消状态。

17\. 后台任务通过受控事务提交文档变更，而不直接修改 UI 状态。

18\. 可撤销命令能执行撤销和重做；不可撤销命令有明确标识。

19\. 插件初始化失败时应用仍可继续运行，并提供日志或诊断信息。

20\. 插件 API 版本不兼容时能够拒绝加载并提供可理解的原因。

21\. 领域 Workbench 不直接依赖 egui 或 GPUI。

22\. 两套 GUI 候选实现可分别验证基础平台能力，但单个产品不同时加载两者。

23\. 产品包只包含该产品选定的 GUI 前端。

\## 18. 实施阶段



\### 阶段 0：验证 GUI 选型和窗口工作区



分别用 egui 和 GPUI 做小型原型，验证：



\- RibbonBar 基础布局和命令绑定；

\- 四周 Dock Panel；

\- 中央多标签内容区；

\- 窗口布局保存与恢复；

\- 普通 GUI 视图和一个可选 GPU 视图；

\- 不同平台的构建和分发体验。



原型用于比较，不代表承诺长期维护两套完整 GUI。



\### 阶段 1：平台最小闭环



实现：



\- 产品入口和静态 Workbench 组合；

\- 命令注册和 RibbonBar；

\- Dock Panel 与中央多标签区；

\- 文档新建、修改、保存和打开；

\- 基本撤销/重做；

\- 工作模式和布局恢复；

\- 任务状态、进度和日志；

\- 一个普通视图和一个可选 `wgpu` 示例视图。



\### 阶段 2：异步命令与事务



实现：



\- 统一命令调用结果；

\- 异步命令和后台任务；

\- 进度、取消、错误和日志；

\- 后台任务与文档事务协调；

\- UI 任务反馈；

\- 文档过期或关闭时的提交策略。



\### 阶段 3：Python 插件闭环



实现：



\- 插件清单和发现；

\- API 版本检查；

\- Python 初始化与插件生命周期；

\- 命令、RibbonBar、菜单和面板扩展；

\- 异步插件命令和进度报告；

\- 插件错误诊断与禁用；

\- 一个示例插件及其自动化测试。



\### 阶段 4：形成平台主线



根据原型和实际 Workbench 开发体验，选定主要 GUI 技术路线。只有在有明确产品需求和维护资源时，才继续维护另一套前端；否则停止扩展其功能。



\### 阶段 5：生产级扩展



根据真实产品需求增加：



\- 插件来源管理和更新机制；

\- 不可信插件的进程隔离协议（如需要）；

\- 大型文档和长任务优化；

\- GPU 资源恢复和视图诊断工具；

\- 崩溃恢复、自动保存和多平台打包；

\- 更完善的自动化和性能测试。

\## 19. 主要风险与应对



| 风险 | 应对 |

|---|---|

| 平台抽象过度，拖慢领域产品实现 | 先做一个完整垂直切片；只抽取实际重复能力 |

| 两套 GUI 长期维护成本过高 | 把它们作为选型原型；根据产品需求收敛主线 |

| RibbonBar 或 Dock 行为在不同 GUI 中不一致 | 明确平台级模型和交互约定；用共同验收测试约束行为 |

| 所有视图被错误地绑定到 GPU 渲染 | 将渲染方式设计为按需能力；普通视图不依赖 `wgpu` |

| GPU 视图持有失效资源 | 由渲染服务管理生命周期；规定设备重建和资源恢复流程 |

| Python 插件被误认为拥有安全沙箱 | 明确安全边界；不可信插件需要独立进程隔离 |

| 后台任务覆盖过期文档状态 | 使用文档版本校验和明确的事务提交边界 |

| UI 抽象无法满足复杂工程面板 | 常见功能使用声明式接口；复杂视图通过有边界的 Rust 扩展实现 |

| 过早使用动态 Rust 插件导致 ABI 复杂 | 初期 Rust Workbench 静态链接 |

| Python 发行和依赖部署不稳定 | 在早期垂直切片中验证解释器、依赖和产品打包 |

\## 20. 最终架构结论



`workbench-rs` 是一个\*\*面向多产品的通用 Workbench 平台\*\*，不是一个同时包含 CAD、机械设计和仿真领域能力的超级应用。



\- 平台提供通用应用运行时、RibbonBar、Dock 工作区、中央多标签内容区、命令、任务、文档基础设施和扩展点；

\- Rust Workbench 模块提供可组合的产品功能；

\- 产品开发者决定模块组合和唯一 GUI 前端；

\- 视图通过统一生命周期接入，可以选择适合自身需求的呈现方式；

\- `wgpu` 是可选渲染能力，只有明确声明需要它的 Rust 视图扩展才获取相应上下文；

\- Python 插件通过版本化 Host API 扩展命令、RibbonBar、面板及受限视图能力；

\- 命令统一支持立即执行、异步执行和后台任务，并由平台提供进度、取消和错误状态；

\- 后台计算与 UI、文档事务之间保持明确边界；

\- 复杂领域核心留在领域模块，通用平台不侵入其数据模型；

\- 开发初期以静态 Rust 模块、典型工作区布局、异步任务和受控 Python 插件实现完整闭环，再根据真实产品需求演进。
